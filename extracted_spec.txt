1. Executive Summary
ScaleAstra is intended to become a multi-tenant AI-assisted sales-automation platform for small and micro product businesses. The first market test should focus on packaged product brands—initially honey and similar natural-food brands—rather than trying to serve every industry at launch.
The commercial approach is hybrid: sell a done-for-you automation setup first, use a reusable core engine and repeatable templates, then productize the common workflows into self-service SaaS only after multiple paying customers prove that the same workflow can be reused.
The first release is a responsive web app, not a native iOS/Android app. It must make core records persistent, protect each business's data, and distinguish demo/simulated integrations from live integrations.

2. Product Strategy and Positioning
2.1 The product promise
Suggested positioning: “WhatsApp Sales Automation for Small Product Brands.” ScaleAstra helps a small product business capture enquiries, respond promptly, manage leads and orders, create invoices, and follow up with eligible customers for repeat purchases.
Sell measurable business outcomes—not “AI” as a buzzword. Potential outcomes include fewer missed enquiries, faster response, more consistent follow-up, clearer order status, and more systematic repeat-customer engagement. Do not promise sales growth until it has been measured.
2.2 Why niche-first, not separate apps
Build one shared platform and one codebase.
Use category-specific workflow templates and configuration, not separate software per business.
Start with one niche because it makes the offer, sales content, onboarding, and workflow more repeatable.
Do not expand to snacks, skincare, retail, or other verticals until the first workflow is reused successfully across several paying customers.

3. Scope: MVP, Later, Out of Scope
3.1 MVP — required
Authentication and business workspace setup.
Business profile: name, category, contact details, currency, time zone and basic preferences.
Dashboard with real counts and recent activity; demo data must be labelled and excluded from live metrics.
Lead CRM: create, view, edit, search, filter, source, status, notes and follow-up date.
Customer records and consent/source records where applicable.
Product catalogue: SKU, name, description, price, category and stock status.
Orders: customer, line items, quantity, totals, delivery details and status lifecycle.
Basic invoice records and printable/downloadable output using validated order data; tax configuration must be explicit.
Predefined workflow execution with trigger, conditions, actions, execution status, errors, idempotency and bounded retries.
Integration settings and explicit live/demo status.
Audit log for important actions and owner notifications.
Basic reporting for lead sources, orders, recorded revenue and conversion, with metric definitions.
3.2 Later, after pilots
AI-assisted lead classification, enquiry summaries and reply drafting.
Repeat-purchase and reorder reminder templates.
One-click campaigns to eligible, opted-in audiences, with preview and approval.
Advanced analytics and campaign attribution.
More industry templates and configurable workflows.
Self-service onboarding, billing, team permissions and integration marketplace.
3.3 Explicitly out of scope for first release
Native mobile app.
Building a WhatsApp API provider, CRM, accounting system or invoice engine from scratch.
Autonomous ad creation, ad-budget changes or campaign launching.
Complex inventory, ERP, shipping or accounting integrations.
A general-purpose drag-and-drop workflow builder.
AI agents independently committing prices, stock, payment status or other consequential business decisions.

Architectural rule: UI, core business logic, database and external integrations must remain separate. Each provider should be behind a server-side adapter so it can be changed without rewriting the entire product.
5.1 Trust boundaries
The browser is not trusted for authorization, price totals, payment state, invoice numbering or secret handling.
Every business-owned record must be scoped to a verified business workspace.
All external webhook payloads must be validated; verify signatures where the provider supports them.
Use server timestamps for trusted audit events.
Do not execute arbitrary code generated by AI as a workflow action.
Demo adapters and live adapters must be visibly and technically separate.

6. Core User Journeys and Workflows
6.1 New lead to order
Meta Form / Website Form / WhatsApp Enquiry
-> validate incoming data
-> normalize contact fields
-> check duplicate / idempotency key
-> record source, timestamp and consent context
-> save lead in database
-> evaluate permitted response rules
-> send approved message through live provider OR mark demo/simulated
-> store provider message ID and delivery status
-> create owner follow-up task/notification
-> customer expresses order intent
-> validate product, quantity, price and availability
-> create order in pending-confirmation state
-> owner verifies stock, delivery and payment evidence
-> confirm appropriate order state
-> generate invoice from validated data
-> fulfil order and record outcome
-> offer eligible post-purchase/reorder workflow
6.2 Workflow engine requirements
Trigger: event that starts a workflow, e.g. lead.created or order.confirmed.
Conditions: deterministic rules, including business settings, consent and current state.
Actions: validated operations such as create task, send approved message, update status or notify owner.
Execution record: workflow ID, business ID, trigger event ID, start/end timestamps, status, attempts and error details.
Idempotency: reprocessing the same event must not duplicate a message, order or invoice.
Retries: bounded retries with backoff for transient failures; do not retry permanent errors indefinitely.
Human approval: required for consequential actions such as unverified payment, price/stock commitments or sensitive outbound campaigns.
Observability: visible execution history and failed-run alerting.
6.3 Order lifecycle
Recommended states: draft → pending_confirmation → confirmed → paid → fulfilled, with cancelled and refunded states where relevant. Define allowed transitions and role permissions. Do not mark paid based only on a customer claim or screenshot; require a trusted payment-provider event or explicit authorized owner verification.
6.4 Messaging rules
Record consent/source and respect opt-outs and applicable provider policies.
Use approved templates and allowed messaging windows where required by the channel.
Do not send promotional messages to every lead by default.
Store send status separately from delivery/read status; a successful API request does not prove delivery.
Provide manual fallback and owner visibility when messaging fails.

9. AI Builder Master Prompt
Use the following master prompt in Google AI Studio Build mode (or adapt it to the selected AI app builder). First ask the builder to plan the architecture, then implement in stages. Do not paste API secrets into the prompt.
Build a production-minded, responsive, multi-tenant web application called ScaleAstra.
PRODUCT PURPOSE
ScaleAstra helps small product businesses automate lead capture, customer follow-up, product catalogue management, order tracking, invoicing and repeat-purchase workflows. The initial niche is small packaged-product businesses, starting with honey and similar natural-food brands. The architecture must support additional industry templates later.
TECHNOLOGY
- Use React with TypeScript for the frontend if supported by the selected builder.
- Use the supported server-side runtime for secure business logic and external API calls.
- Use Firebase Authentication and Cloud Firestore for login and persistent storage, subject to platform compatibility.
- Keep the architecture modular and suitable for gradual SaaS expansion.
- Use server-side secret management for API credentials.
- Do not introduce paid dependencies unless explicitly approved.
DESIGN
Create a professional, premium SaaS dashboard with a restrained dark-purple and white interface, accessible contrast, clear typography, responsive tables and mobile-friendly navigation. Avoid unnecessary visual complexity.
CORE MODULES
1. Authentication and business workspace setup.
2. Dashboard with leads, orders, recorded revenue and recent activity.
3. Lead CRM with source, status, contact details, notes, timestamps and follow-up date.
4. Customer database with purchase history and consent records.
5. Product catalogue with SKU, description, price, stock status and category.
6. Orders with line items, quantities, totals, delivery details and lifecycle status.
7. Invoices based on validated order data, with printable/downloadable output.
8. Automation engine with triggers, conditions, actions, execution history and errors.
9. Messaging templates and integration status.
10. Reports for lead sources, conversion, orders and recorded revenue.
11. Settings for business details, users, roles and integrations.
12. Audit log for important business actions.
MULTI-TENANT SECURITY
Every business-owned record must include businessId. Every authenticated user must have explicit workspace membership and a role. Users must only access records belonging to workspaces they are authorized to access. Enforce this in database security rules and server-side authorization, not only in the UI. Do not trust a client-supplied businessId without verifying membership. Do not expose secrets in browser code.
DATA MODELS
Define appropriate structures for users, businesses, memberships, leads, customers, products, orders, invoices, workflowDefinitions, workflowExecutions, integrationSettings, consentRecords and auditLogs. Include createdAt, updatedAt and relevant status fields. Define relationships, validation rules and deletion/retention behaviour. Use trusted server timestamps for audit events.
LEAD WORKFLOW
Accept leads through a documented internal API or test form. Validate input, normalize fields, deduplicate where possible, record the source and save the lead. Check consent and messaging eligibility before sending any message. Provide owner notification and a clear failure state.
AUTOMATION ENGINE
Implement a small deterministic workflow engine. Support explicit triggers, conditions and actions. Include execution IDs, idempotency, bounded retries, timestamps, success/failure states and error logs. Do not execute arbitrary generated code or allow an AI model to invent unrestricted actions.
ORDERS AND INVOICES
Support draft, pending confirmation, confirmed, paid, fulfilled, cancelled and refunded states where appropriate. Verify payment through a trusted source or explicit authorized owner confirmation. Never assume payment is complete merely because a customer says they paid. Generate invoice records only from validated order data. Make tax settings configurable; do not invent tax rates.
META AND WHATSAPP
Create clean server-side integration interfaces for Meta lead capture and the configured WhatsApp Business Platform provider. Build settings and status screens. Until credentials, permissions, webhook verification and API access are configured, use a clearly labelled demo adapter. Never expose tokens or webhook secrets in client code. Respect consent, templates and applicable messaging rules. Store credentials only in secure server-side secrets.
DASHBOARD AND REPORTING
Display total leads, qualified leads, orders, conversion rate, recorded revenue and recent activity. Explain metric definitions. Exclude demo records from live metrics. Do not fabricate data or claim campaign results that are not measured.
AI FEATURES
Make AI-assisted lead classification and reply drafting optional. Keep prices, stock commitments, payment verification, invoice issuance and other consequential decisions under explicit business rules and/or human approval.
QUALITY REQUIREMENTS
Provide CRUD functionality, validation, search, filters, loading states, empty states, error handling and mobile responsiveness. Use reusable components and a maintainable folder structure. Include setup instructions, environment variable documentation, database schema documentation, security rules, README and a manual test checklist.
BUILD PROCESS
First produce an implementation plan and architecture. Then build the application in stages, test each stage, fix errors and explain what is complete, what is simulated and what remains unconfigured. Prioritize a functioning, secure MVP over unnecessary features.

15. Missing Items and Risk Signals — Resolve Before Production
This section is deliberately direct. The current concept is promising as a testable direction, but several critical decisions remain open. A developer should not silently guess these.
15.1 Product and commercial gaps
Niche is a hypothesis, not validated demand. Interview owners and obtain paid pilots before broadening categories.
The buyer and user may differ. Define whether the owner, sales operator or agency user controls the workspace.
Define exact pilot deliverables, support hours, service-level expectations, onboarding responsibilities and cancellation terms.
Define pricing treatment for provider charges, ad spend, tax and custom work.
Define how a customer can export data and leave the platform.
15.2 Technical gaps
Exact builder-generated framework and server runtime must be inspected before finalizing implementation details.
Meta app setup, permissions, lead access, app review requirements and webhook configuration need verification.
MSGPEDIA integration capabilities are not yet confirmed: API docs, inbound webhooks, outbound sends, delivery callbacks, template support, tenant isolation, rate limits and commercial reuse permissions.
Payment gateway is undecided. Decide whether MVP uses manual owner verification or a verified payment-provider integration.
Invoice requirements must be reviewed for the business's jurisdiction, tax registration and invoice type.
Need backup/restore, error monitoring, workflow queue strategy, rate limiting, abuse prevention and integration health checks before wider deployment.
Need a production deployment plan, custom domain, TLS, environment separation, and an explicit rollback/restore procedure.
Need a defined test suite and human review of generated code and rules; successful compilation is not proof of security.
15.3 Privacy, security and compliance gaps
Define a privacy notice, lawful collection purpose, retention period, deletion/export process and customer support contact.
Store consent evidence and implement opt-out/suppression lists for applicable messaging.
Review applicable Indian data protection, consumer, tax and messaging requirements with a qualified professional before live commercial use.
Restrict access to personal data by role; avoid logging access tokens, payment data or unnecessary customer content.
Define incident response, credential rotation, backup retention and account offboarding.
Do not use real customer data in public AI prompts or unapproved demo environments.

18. Final Recommendation
Build a secure, persistent lead-to-order workflow before attempting a broad automation platform. Use AI to accelerate implementation, not to bypass product decisions, security review or testing. The first milestone is three paying businesses using substantially the same workflow with limited customization. If each customer requires a different system, do not call it scalable SaaS yet.
Immediate founder actions: (1) interview ten target businesses; (2) verify MSGPEDIA API/webhook capabilities and Meta access; (3) build the lead/product/order MVP; (4) obtain at least one paid pilot; (5) measure setup time, operating cost and actual workflow outcomes.
